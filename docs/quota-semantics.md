# 多租户配额与公平调度：语义说明

本文描述 `quota-gateway` 在**单实例**与**多实例**部署下的配额判定、
公平调度、释放、热更新与降级语义。

## 1. 三维配额

配额按 `(租户 tenant, 接口 api)` 维度配置，每条规则包含：

| 字段 | 含义 | 取值与语义 |
| --- | --- | --- |
| `rate` | 平均速率（令牌/秒） | 令牌桶补充速度；`0` 表示不限速 |
| `burst` | 突发容量（令牌桶大小） | 允许的瞬时突发；`rate>0` 时必须 `>=1` |
| `maxConcurrent` | 租户在该接口的在途请求上限 | 硬上限，`0` 表示不限 |
| `weight` | 公平调度权重 | 容量竞争时的分享比例；`<=0` 取 `defaultWeight` |

另有全局字段 `globalMaxConcurrent`：所有租户共享的在途容量池。
- 接口专属规则优先于“租户默认规则”（`api` 为空串的规则）。
- 未配置任何规则的租户不施加配额（直接放行）。

### 判定顺序（单条原子操作）

每个请求在存储后端以**一个原子操作**完成以下判定，顺序固定：

1. **速率**：惰性补充令牌桶，令牌不足 → `rate_limited`（立即拒绝）。
2. **租户并发硬上限**：在途数达到 `maxConcurrent` →
   `concurrency_limited`（立即拒绝，不排队）。
3. **共享容量池**：全局在途数达到 `globalMaxConcurrent` →
   进入公平队列（不立即拒绝，见第 2 节）。
4. 三步均通过：扣减 1 个速率令牌，同时在“租户键”和“共享键”占位，请求放行。

> 速率令牌**不会**因请求结束/拒绝而归还：被拒或降级放行的请求未被服务，
> 不应回补令牌；令牌只随时间按 `rate` 恢复，避免“拒绝放大额度”。

## 2. 加权公平调度与容量借用

当且仅当配置了 `globalMaxConcurrent` 时启用。

- 采用加权虚拟完成时间（WFQ/GPS 近似）：每个请求的虚拟完成时间
  `F = max(flow.finish, V) + 1/weight`，等待请求严格按 `(F, 到达顺序)`
  升序成为队首；`V` 为当前忙碌租户中最小的 `finish`。
- 权重越大，单位时间被放行的请求越多——**不同租户按 `weight` 比例
  分享共享容量**，权重 4 与权重 1 的租户在持续竞争下约获得 4:1 的服务机会。
- 队首在共享池占满时不抢占，而是在队列内等待；当任意在途请求释放
  （`Release` 广播）时被唤醒重试，因此队列一定可以被排空，不会死锁，
  也不会因为“只试一次”而错误拒绝本可被服务的请求。
- 某租户完全闲置（在途与排队均为 0）后，其虚拟基线对齐当前系统进度：
  **其闲置容量可被其他租户临时借用；当它再次需要时不会被陈旧的高
  finish 长期压制，也不会凭陈旧的低 finish 插队**——容量在需要时被归还。

排队时长同时受调用方 `context` 截止时间与服务端 `QueueTimeout`
（默认 1s）约束；排队超时按 `concurrency_limited` 稳定拒绝并给出
`Retry-After`。客户端取消（断开连接）会立即退出队列，不产生占位。

## 3. 拒绝错误与重试提示

拒绝以稳定、可区分的形式返回（HTTP 映射见下），均带机器可读错误码，
并在可预估时给出 `Retry-After`：

| 错误码 | 触发条件 | HTTP | Retry-After |
| --- | --- | --- | --- |
| `rate_limited` | 速率/突发超限 | 429 | 距下一个令牌的时间（向上取整秒） |
| `concurrency_limited` | 租户并发硬上限 / 公平排队超时 | 429 | 最近占位预计释放时间 |
| `degraded_deny` | 后端不可用且策略为 deny | 503 | 无（错误码见 `X-Quota-Reason`） |

- 速率受限的 `Retry-After` 由令牌桶精确计算；
- 并发受限的 `Retry-After` 取当前最早一个占位的 TTL 剩余时间（兜底 10ms）。
- 响应体为 JSON：`{"error":{"code","message","retry_after_seconds"}}`。

未超限请求不会被误伤：原子判定先查后占，且公平队列只在“共享池确实占满”
时让请求等待。

## 4. 多实例一致性

所有配额状态集中存储在 **Redis**（生产）或进程内内存（单实例/本地）：

- `TryAcquire` 是一段 Redis Lua 脚本，在 Redis 单线程内原子执行
  “补令牌→速率判定→租户上限判定→共享池判定→扣令牌+两处占位”，
  因此**多个网关实例并发时，全局速率与并发占用严格一致**。
- 每个并发占位带全局唯一凭证 `token`（`实例ID-进程内自增序号`，实例ID
  含主机名/PID/随机后缀），**实例增减、重启、短暂不可达都不会造成
  重复计数或额度放大**。
- 占位带 TTL（默认 30s）并由**在途租约续租**配合工作（见第 5 节）：
  请求正常在途时名额被持续续租、不会被提前回收；若实例崩溃、网络分区
  导致续租与 `Release` 都停止，过期占位会在后续判定时被**惰性回收**
  （有界时间，不超过 TTL），不会永久泄漏，也不会把额度放大。
- Lua 脚本通过 `SCRIPT LOAD` + `EVALSHA` 执行；主从切换/重启清空脚本
  缓存返回 `NOSCRIPT` 时自动回退 `EVAL` 并重新加载，对调用方透明。

> 内存存储仅在单进程内保证一致；多实例部署务必使用 Redis。

## 5. 长连接的名额保留与释放

**保留（租约续租）**：每次成功获取都会在本实例登记一条租约
（token + 占位键 + 调用方 ctx）。Manager 内**唯一一个后台循环**
（与连接数无关，无每连接 goroutine/定时器）周期性地：

1. **续租（确保名额存在）**：按占位键集合分组，每组一次存储调用，
   把仍存活租约的过期时间延长到 `now + ConcurrencyTTL`（默认续租周期
   为 TTL 的 1/3）。因此**只要请求仍在处理且持有实例存活，名额就一直
   被占用**——即使单个请求持续数分钟、远超 TTL，该租户任意时刻的在途
   数也不会超过 `maxConcurrent`。
   - **名额中途丢失的兜底**：若后端记录丢失（后端重启/抖动、或一段
     时间连不上后端导致记录过期），续租会**按原样重建**该 token 的
     占位，并以 `lost` 列表返回；Manager 逐条记日志并累计
     `lease_restored_total` / `lease_restored_by_key` 指标。也就是说，
     请求仍在正常处理、持有实例还活着时，名额不会被提前归还，新请求
     不会因此超量进入；丢失事件本身可观测，不会悄悄发生。
   - **不复活已释放名额**：Manager 只对“本地仍登记为在途”的 token
     续租（释放前先从租约表摘除，续租前再按最新租约表过滤一次）。
     释放与续租的极端并发交错最多留下一个 TTL 周期内的占位残留
     （有界，随过期自动消失），不会永久泄漏、不会重复计数。
2. **断连回收**：发现租约的 ctx 已取消（客户端断连而 handler 仍未
   返回）时，触发与正常结束完全相同的幂等释放（默认检查周期 100ms，
   可用 `ReapInterval` 调整）。回收在单飞 goroutine 中执行，后端缓慢
   时不会阻塞续租职责。

**崩溃回收**：实例被强杀后续租停止，其遗留占位在 `ConcurrencyTTL`
内有界回收——既不永久卡住后续请求，也不会因提前回收而放大额度。

**释放（任意交错安全）**：`ReleaseFunc` 内部用 `sync.Once` 保护，
以下路径以任意顺序、任意并发交错触发都安全，进程不会退出：

- 上游 handler **正常返回**（中间件 `defer` 释放）；
- handler **panic** / 请求**超时**；
- **客户端中断**（后台循环回收，见上）；
- **重复释放、乱序释放**：均为无副作用空操作；释放脚本仅在 `token`
  仍是有效占位时删除，不会误删他人名额。

释放使用**独立的 context + 超时**（2s），即使原请求已取消也会尽力释放；
若释放仍失败（后端长时间不可达），依赖占位 TTL 兜底回收，绝不成永久泄漏。
中间件本身不创建任何每请求 goroutine：数千条并发长连接集中释放时，
释放动作不阻塞请求主路径，协程与内存占用不随连接数无界增长。

## 6. 配置热更新与版本演进

- 配置为 JSON，含 `version`（语义化 `MAJOR.MINOR[.PATCH]`）。
- **新配置生效前必须通过 `Validate`**：字段范围、`rate>0⇒burst>=1`、
  `(tenant,api)` 不重复等；JSON 解析对未知字段报错，避免旧实例误用新语义。
- 版本兼容规则：仅接受与本实例**主版本号相同**且不低于
  `MinSupportedConfigVersion`（1.0）的配置；主版本不兼容或过旧的配置被拒绝。
  同一主版本内允许升级或回退，从而支持**新旧版本实例滚动共存**。
- 校验失败、解析失败、版本不兼容时，**保留正在使用的旧配置不变**，
  仅记录日志与 `invalid` 指标；只有校验通过的配置才会原子替换。
- 令牌桶热更新即时生效：容量缩小时当前令牌随之封顶；容量放大时不额外
  补发令牌（只随时间累积），避免“改配置瞬间放大额度”。
- **长连接进行中的热更新**：在途租约的占位键在获取时确定，续租与释放
  不依赖当前配置——配置变更（含放宽/收紧上限、删除规则）不会导致在途
  名额被误回收或重复占用；新请求按新配置判定。
- 示例服务通过 **SIGHUP** 与**文件 mtime 轮询**（默认 2s）触发重载。

## 7. 降级策略（配额后端不可用）

由配置 `degrade` 决定，必须显式、可解释：

- `deny`（默认，fail-closed）：后端不可用时拒绝请求，返回 503 +
  `degraded_deny`。适合配额正确性优先、不允许超额的场景。
- `allow`（fail-open）：后端不可用时放行请求，但**仍受本地并发硬上限
  约束**（见下），保证可用性的同时不会拖垮实例。

### 降级放行的本地兜底（fail-open 的硬上限）

降级放行**不占用**后端额度，改为在本实例按 `(租户, 接口)` 计数：

- 上限取该规则的 `maxConcurrent`；规则未配置时取 Manager 选项
  `DegradeMaxConcurrent`（默认 1024）。达到本地上限的新请求按
  `concurrency_limited`（429）拒绝，可解释、带重试提示。
- **上限判定是合并口径**：本实例上“故障前经后端正常计账、仍在运行
  的在途”也算入。实现上，规则配置了 `maxConcurrent` 的获取在访问后端
  **之前**先本地预留名额（后端失败回滚、进入降级时转换为降级在途、
  请求结束回收），因此“故障前已在跑的 + 放行期间新进的”之和**绝不
  超过配置上限**——不会出现两批各算各的、合计到上限两倍的情况。
- 本地视图可直接观测：`Manager.LocalInflight(tenant, api)` 返回
  （后端计账在途, 降级兜底在途），指标侧有 `inflight_by_key`（总在途）
  与 `degraded_inflight_by_key`（其中放行期间进来的部分），上限即配置
  中的 `maxConcurrent`——无需查询后端即可核对。
- 本地计数随请求结束/断连正常回收（复用租约回收机制）。
- **恢复计账**：降级期间的在途请求始终只计在本地、从不写入后端，
  因此后端恢复后不会被重复计数；同时正常获取路径会把本地在途数从
  租户硬上限中**扣除**，使“后端占用 + 本地降级在途”之和不超过
  `maxConcurrent`（不放大额度），本地在途随请求结束自然归零后恢复全额。
  （多实例各自只扣自己的本地在途：恢复瞬间的过渡超出有界且自愈。）

为避免级联故障：
- 每次存储调用都带超时（连接/脚本级），后端慢或不可达不会无限阻塞 worker；
- 健康监测（默认 1s 探测）只在**状态翻转**时记录日志，避免故障期日志风暴；
- 后端恢复后请求立即恢复正常判定，不残留降级状态。

拒绝原因与当前状态通过结构化日志与 `/debug/vars`（expvar）指标观测：
请求/放行/拒绝（按租户、接口、原因）、降级动作与降级在途、在途数、
名额丢失重建（`lease_restored_total` / `lease_restored_by_key`）、
后端健康、配置版本、判定延迟等。

## 8. 可调优项（均可选，有默认值）

Manager 选项（示例服务以同名 CLI 参数暴露）：

| 选项 | 默认 | 含义 |
| --- | --- | --- |
| `ConcurrencyTTL` / `-concurrency-ttl` | 30s | 并发占位 TTL：实例崩溃后名额的有界回收时间 |
| `RenewInterval` / `-renew-interval` | TTL/3 | 在途租约续租周期（长连接名额保活） |
| `ReapInterval` / `-reap-interval` | 100ms | 断连租约的后台回收检查周期 |
| `QueueTimeout` / `-queue-timeout` | 1s | 共享容量竞争的公平排队最长等待 |
| `DegradeMaxConcurrent` / `-degrade-max-concurrent` | 1024 | 降级放行时规则未配上限的本地在途硬上限 |

以上均为进程级调优，与配额配置文件无关；既有配置文件无需任何改动。
