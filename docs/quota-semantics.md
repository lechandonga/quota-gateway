# 配额语义说明

本文档描述 quota-gateway 的精确行为，便于二次开发与运维排障。

## 1. 两个独立维度

一次 `Acquire(tenant, iface)` 顺序经过两道关卡，任一不过即拒绝：

1. **速率桶（平均速率 + 突发）**：惰性填充的令牌桶。
   - `RatePerSec`：每秒补充的令牌数（平均吞吐上限）。
   - `Burst`：桶容量（允许的瞬时突发）。
   - 取 1 令牌失败返回 `rate_limited`，并给出精确 `RetryIn`
     （`ceil(缺口 / rate)`）。
   - 令牌只在访问时按真实经过时间补充，没有后台协程，因此速率恢复与时钟严格一致。
2. **并发准入（硬上限 + 组公平）**：
   - `MaxConcurrent`：该租户/接口同时在途请求的**硬上限**，超过立即
     返回 `concurrent_limit`，不排队。
   - 若该租户/接口属于某个容量组 `Group`，还要通过组内加权公平裁决
     （见下节）。未获得份额时在 `MaxWait` 内做有界退避重试，超时返回
     `fairness_wait`。

未配置的租户/接口两道关卡都跳过：**直接放行、零计数、零外部调用**，
因此依赖故障也不会波及它们。

## 2. 加权公平与闲置借用

每个 `Group` 有总 `Capacity`，组成员有 `Weight`。裁决遵循三条规则：

1. **加权保证份额**：在“已被争夺的容量”上按权重比例分配。
   - “已被争夺的容量”= `max(当前总占用, 1)`。完全没人使用的容量是
     **闲置容量**，不预先划分给任何人。
   - 这样保证：后来的租户出现时，不会追溯削减先到租户已经在使用的容量。
2. **闲置借用**：当一个租户当前占用已达到其保证份额，而组内仍有
   物理空闲名额、且没有其他“排队中且低于份额”的成员时，允许它借用
   闲置容量。闲置容量因此不会被浪费，整体吞吐保持在容量上限附近。
3. **原租户收回**：一旦原租户（或任何排队成员）当前占用低于其加权份额，
   借用方将**不能再获得新名额**；随着借用方请求结束释放名额，空闲名额
   会优先准入低于份额的等待者，容量自然“归还”。没有强制抢占正在处理的
   请求——这保证了长连接不被中途打断，同时杜绝借用人长期饿死他人。

### 裁决是确定性纯函数

所有准入在协调端（多实例）或网关内（单实例）的**单一互斥锁**下串行执行，
公平逻辑本身是无副作用的纯函数 `decideAdmit(snapshot)`。相同快照必然得到
相同结果，因此高并发下不会因“多个请求同时看到一个空位”而超额准入。

### 排队身份（demand）与 TTL

- 某个成员一旦在组满时申请，即记录“排队中”身份及时间戳；
  成功获得名额后立即清除。
- 排队身份有 2 秒 TTL：期间每次申请都会刷新；超过 TTL 没有新申请则视为
  放弃竞争，身份被回收（防止崩溃的等待者永久阻止他人借用闲置容量）。

## 3. 多实例一致性

多实例下全部状态在 `coordserver` 单点维护，正确性由以下机制保证：

### 3.1 幂等键：防重复计数

- 准入请求携带调用方生成的 `RequestID`，以及公平排队的 `Attempt` 序号。
  幂等单元是 **(RequestID, Attempt)**。
- **网络重试**（响应丢失后重发同一个 Attempt）：服务端返回首次裁决，
  绝不占用第二个名额。
- **公平排队重试**（等待后新一轮）：使用新的 Attempt，是独立裁决，
  允许在容量变化后准入。
- **速率扣减**有独立的一次性 `dedupKey`（每个逻辑请求一个）：即使取令牌
  请求超时但服务端实际已扣，重发也返回首次结果，**一次请求只扣一个令牌**，
  不会因网络重放而缩小可用额度。
- 释放请求同样按 `RequestID` 幂等；重复释放、乱序释放、未知凭证一律
  安全 no-op。
- 三类幂等记录（准入/释放/速率）均带 **10 分钟 TTL** 并由后台回收，
  避免长期运行无界增长；其中“凭证仍持有”的准入记录在释放前不会被清理，
  保证旧 ID 重放始终安全。

### 3.2 会话租约与 TTL：防额度泄漏与放大

- 每个实例启动时向协调端注册带 TTL 的会话，并按心跳间隔续约。
- 每次准入产生的租约绑定到会话。
- **实例崩溃 / 网络分区 / 被驱逐**：心跳停止，会话到期后协调端
  原子释放该会话名下**全部**租约。因此：
  - 额度不会因为实例消失而泄漏（名额被回收，可被他人使用）；
  - 旧实例稍后恢复或迟到的 Release 到达时，凭证已不存在，按 no-op 处理，
    不会重复归还（不会“放大”额度）。
- **实例重启**：生成新的随机会话标识，与旧会话区分；旧占用仍由 TTL 回收。
- **协调服务重启**：网关心跳收到 409 后自动重新注册；在协调端不可达期间
  按降级策略处理（见 `degradation.md`）。

### 3.3 速率一致性

速率桶只存在于协调端，所有实例共享同一个桶，因此“同一租户的平均速率”
在集群范围内严格成立，与请求落在哪个实例无关。

## 4. 长连接释放契约

获得的 `Lease` 必须在**所有**结束路径上调用 `Release()`，包括：

- 正常处理结束；
- 上游/下游处理超时（`context.WithTimeout` 到期）；
- 客户端中断（请求 context 被取消）；
- handler panic（通过 `defer lease.Release()` 保证）。

`Release()` 内部用 `sync.Once` 保护，重复调用安全；内部释放失败也不
panic（协调端会话/租约 TTL 是最终兜底）。建议写法：

```go
lease, err := gw.Acquire(r.Context(), tenant, iface)
if err != nil { return err }
defer lease.Release()
```

## 5. 配置版本与兼容性

- 配置带 `APIVersion`（如 `v1`）与单调递增的整数 `Version`。
- **主版本不同** → 拒绝（语义可能不兼容）；同主版本内向前/向后兼容：
  协议层忽略未知字段，新增字段都有安全默认值，因此新旧实例可以在
  滚动发布期间共存。
- **Version 回退** → 拒绝，防止乱序下发覆盖新配置；相同 Version 幂等接受。
- 热更新顺序：本地校验 → 协调端校验安装 → 本地原子提交。任何一步失败，
  正在使用的配置完全不变。
- 速率桶热更新：新速率立即生效；突发缩小会把当前令牌收敛到新上限，
  突发放大**不补发**历史令牌（避免更新瞬间凭空产生额度）。
