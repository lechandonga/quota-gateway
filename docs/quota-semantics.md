# 多租户配额与公平调度：语义说明

本文描述 `quota-gateway` 在**单实例**与**多实例**部署下的配额判定、
公平调度、释放、热更新与降级语义。

## 1. 三维配额

配额按 `(租户 tenant, 接口 api)` 维度配置，每条规则包含：

| 字段 | 含义 | 取值与语义 |
| --- | --- | --- |
| `rate` | 平均速率（令牌/秒） | 令牌桶补充速度；`0` 表示不限速 |
| `burst` | 突发容量（令牌桶大小） | 允许的瞬时突发；`rate>0` 时必须 `>=1` |
| `maxConcurrent` | 租户在该接口的在途请求上限 | 硬上限，`0` 表示不限 |
| `weight` | 公平调度权重 | 容量竞争时的分享比例；`<=0` 取 `defaultWeight` |

另有全局字段 `globalMaxConcurrent`：所有租户共享的在途容量池。
- 接口专属规则优先于“租户默认规则”（`api` 为空串的规则）。
- 未配置任何规则的租户不施加配额（直接放行）。

### 判定顺序（单条原子操作）

每个请求在存储后端以**一个原子操作**完成以下判定，顺序固定：

1. **速率**：惰性补充令牌桶，令牌不足 → `rate_limited`（立即拒绝）。
2. **租户并发硬上限**：在途数达到 `maxConcurrent` →
   `concurrency_limited`（立即拒绝，不排队）。
3. **共享容量池**：全局在途数达到 `globalMaxConcurrent` →
   进入公平队列（不立即拒绝，见第 2 节）。
4. 三步均通过：扣减 1 个速率令牌，同时在“租户键”和“共享键”占位，请求放行。

> 速率令牌**不会**因请求结束/拒绝而归还：被拒或降级放行的请求未被服务，
> 不应回补令牌；令牌只随时间按 `rate` 恢复，避免“拒绝放大额度”。

## 2. 加权公平调度与容量借用

当且仅当配置了 `globalMaxConcurrent` 时启用。

- 采用加权虚拟完成时间（WFQ/GPS 近似）：每个请求的虚拟完成时间
  `F = max(flow.finish, V) + 1/weight`，等待请求严格按 `(F, 到达顺序)`
  升序成为队首；`V` 为当前忙碌租户中最小的 `finish`。
- 权重越大，单位时间被放行的请求越多——**不同租户按 `weight` 比例
  分享共享容量**，权重 4 与权重 1 的租户在持续竞争下约获得 4:1 的服务机会。
- 队首在共享池占满时不抢占，而是在队列内等待；当任意在途请求释放
  （`Release` 广播）时被唤醒重试，因此队列一定可以被排空，不会死锁，
  也不会因为“只试一次”而错误拒绝本可被服务的请求。
- 某租户完全闲置（在途与排队均为 0）后，其虚拟基线对齐当前系统进度：
  **其闲置容量可被其他租户临时借用；当它再次需要时不会被陈旧的高
  finish 长期压制，也不会凭陈旧的低 finish 插队**——容量在需要时被归还。

排队时长同时受调用方 `context` 截止时间与服务端 `QueueTimeout`
（默认 1s）约束；排队超时按 `concurrency_limited` 稳定拒绝并给出
`Retry-After`。客户端取消（断开连接）会立即退出队列，不产生占位。

## 3. 拒绝错误与重试提示

拒绝以稳定、可区分的形式返回（HTTP 映射见下），均带机器可读错误码，
并在可预估时给出 `Retry-After`：

| 错误码 | 触发条件 | HTTP | Retry-After |
| --- | --- | --- | --- |
| `rate_limited` | 速率/突发超限 | 429 | 距下一个令牌的时间（向上取整秒） |
| `concurrency_limited` | 租户并发硬上限 / 公平排队超时 / 恢复过渡期本地闸门满 | 429 | 最近占位预计释放时间 |
| `degraded_local_concurrency_limited` | 后端不可用 fail-open 期间达到本实例本地并发硬上限 | 429 | 1s |
| `degraded_deny` | 后端不可用且策略为 deny | 503 | 无（错误码见 `X-Quota-Reason`） |

- 速率受限的 `Retry-After` 由令牌桶精确计算；
- 并发受限的 `Retry-After` 取当前最早一个占位的 TTL 剩余时间（兜底 10ms）。
- 响应体为 JSON：`{"error":{"code","message","retry_after_seconds"}}`。

未超限请求不会被误伤：原子判定先查后占，且公平队列只在“共享池确实占满”
时让请求等待。

## 4. 多实例一致性

所有配额状态集中存储在 **Redis**（生产）或进程内内存（单实例/本地）：

- `TryAcquire` 是一段 Redis Lua 脚本，在 Redis 单线程内原子执行
  “补令牌→速率判定→租户上限判定→共享池判定→扣令牌+两处占位”，
  因此**多个网关实例并发时，全局速率与并发占用严格一致**。
- 每个并发占位带全局唯一凭证 `token`（`实例ID-进程内自增序号`，实例ID
  含主机名/PID/随机后缀），**实例增减、重启、短暂不可达都不会造成
  重复计数或额度放大**。
- 占位是一个带 **TTL 的租约（lease）**：持有者实例存活时，由实例内唯一
  的后台续租 goroutine 周期性把所有在途占位的到期时间向后延长（见第 5
  节），因此请求即使运行数分钟/数小时也不会被提前回收；实例崩溃、被强
  杀或网络分区导致续租停止时，遗留占位在**一个 TTL 的有界时间内**被后
  端惰性回收（后续 `TryAcquire` 或续租调用时清理），不会永久卡住后续
  请求，也不会放大额度。
- Lua 脚本通过 `SCRIPT LOAD` + `EVALSHA` 执行；主从切换/重启清空脚本
  缓存返回 `NOSCRIPT` 时自动回退 `EVAL` 并重新加载，对调用方透明。

> 内存存储仅在单进程内保证一致；多实例部署务必使用 Redis。

## 5. 长连接名额：租约保留、续租与释放

### 5.1 存活期间名额稳定（续租）

获取名额时写入的占位带租约 TTL（默认 30s）。**Manager 内只有一个续租
goroutine**（不随连接数增长，数千条长连接共享同一个周期定时器），它按
`TTL/3` 的周期（钳制在 100ms–10s）扫描本实例登记在册的全部凭证，调用
单条原子 Lua 脚本 `Renew`：

- 凭证在**每个**占位键（租户键、共享键）上都仍存在且未过期 → 整体把到
  期时间延长到 `now+TTL`，返回成功；
- 任一键上凭证已被删除或已过期 → **不修改任何键**并返回“凭证丢失”。

因此：只要请求仍在正常处理、且持有它的实例还活着，名额就一直被该请求
稳定占用；同一租户任意时刻运行的请求数绝不超过配置上限。续租与正常
`Release` 的交错由“先摘除登记、再释放；续租成功后复核登记并补偿释放”
的顺序保护，不会出现“已释放的名额被续租复活”。

### 5.2 实例故障后的有界回收

实例崩溃 / 被 `SIGKILL` 强杀 → 续租 goroutine 一并消失，也不会有人调用
`Release`。遗留占位在最多一个 TTL 后被后端判定过期并在下次访问时惰性
回收，后续请求在有界时间内即可获得名额。可通过配置把 TTL 调小以缩短
故障回收时间（代价是续租更频繁）。

> 极端情况：存活实例与后端的网络分区持续超过 TTL，后端会回收其占位并
> 可能把名额分给其他实例；恢复连接后续租发现“凭证丢失”，本实例不会再
> 用旧凭证占位（避免重复计数），本地仍保守地把该名额计入占用直到请求
> 结束，并通过日志与 `lease_lost_total` 指标暴露该事件。这是分布式系统
> 在无共识协议下的标准取舍：宁可分区窗口内少放行，不放大多放行。

### 5.3 释放路径的并发安全

中间件保证以下任一路径都会**恰好一次**释放并发占用：

- 上游 handler **正常返回**；
- handler **panic**（中间件 recover 兜底返回 500，同时 `defer` 释放）；
- 请求**超时**；
- **客户端中断**（`r.Context()` 取消，中间件监听其 `Done()`）。

释放动作由 `sync.Once` 保护：**“客户端中断”与“handler 恰好结束”同时
发生**（持续压测下高频出现的交错）时也只释放一次，旧实现中
`select + close(chan)` 非原子导致的 double-close panic 已修复；重复调用、
乱序调用、异常路径二次释放均为无副作用空操作；后端释放脚本仅在
`token` 仍是有效占位时删除。释放使用**独立的 context + 超时**（2s），
即使原请求已取消也会尽力释放；若释放仍失败（后端长时间不可达），依赖
租约 TTL 兜底回收，绝不成永久泄漏。

## 6. 配置热更新与版本演进

- 配置为 JSON，含 `version`（语义化 `MAJOR.MINOR[.PATCH]`）。
- **新配置生效前必须通过 `Validate`**：字段范围、`rate>0⇒burst>=1`、
  `(tenant,api)` 不重复等；JSON 解析对未知字段报错，避免旧实例误用新语义。
- 版本兼容规则：仅接受与本实例**主版本号相同**且不低于
  `MinSupportedConfigVersion`（1.0）的配置；主版本不兼容或过旧的配置被拒绝。
  同一主版本内允许升级或回退，从而支持**新旧版本实例滚动共存**。
- 校验失败、解析失败、版本不兼容时，**保留正在使用的旧配置不变**，
  仅记录日志与 `invalid` 指标；只有校验通过的配置才会原子替换。
- 令牌桶热更新即时生效：容量缩小时当前令牌随之封顶；容量放大时不额外
  补发令牌（只随时间累积），避免“改配置瞬间放大额度”。
- **长连接在途期间热更新安全**：占位键由 `(租户,接口)` 与唯一 token
  决定，不随配置改变；配置切换不触碰既有占位与续租登记，正在运行的长
  请求既不会被误回收，也不会被重复占用。并发上限调整对**后续**判定立即
  生效（调大立即放行更多、调小不抢占已在途请求，只阻止新请求）。
- 可选字段 `concurrencyTTLSeconds`（租约 TTL，秒）也可热更新：新值对
  新占位与后续续租立即生效，范围 `0`（用实例默认 30s）到 `3600`，非法
  值被拒绝并保留旧配置。
- 示例服务通过 **SIGHUP** 与**文件 mtime 轮询**（默认 2s）触发重载。

## 7. 降级策略（配额后端不可用）

由配置 `degrade` 决定，必须显式、可解释：

- `deny`（默认，fail-closed）：后端不可用时拒绝请求，返回 503 +
  `degraded_deny`。适合配额正确性优先、不允许超额的场景。
- `allow`（fail-open）：后端不可用时放行请求，保证可用性；**但放行不
  再是无约束的**（见 7.1）。适合可用性优先、上游另有保护的场景。

### 7.1 降级放行时的本地并发硬上限

后端不可用时无法集中计账，网关在**本实例内**为每个 `(租户,接口)` 维护
一个本地并发闸门，容量就是规则配置的 `maxConcurrent`：

- 降级放行的请求先占用本地名额，达到 `maxConcurrent` 后新请求被稳定
  拒绝（HTTP 429，`X-Quota-Reason: degraded_local_concurrency_limited`，
  带 `Retry-After`），避免故障期本地在途无限堆积拖垮实例；
  `maxConcurrent=0`（不限并发）的规则不施加本地上限；
- 本地在途数通过指标 `degraded_local_inflight` 实时可观测，请求结束即
  归还，行为与正常释放一样幂等。

### 7.2 后端恢复后的统一计账（不放大、不重复计数）

降级期间仍在运行的请求**继续保留本地名额直到自己结束**；后端恢复后到
达的新请求由后端原子判定统一计账，并同样尝试本地闸门：

- 稳态（无降级遗留在途）时，后端硬上限已保证本实例在途
  `<= maxConcurrent`，本地闸门恒有余量，不引入额外拒绝；
- 恢复过渡期若降级遗留尚未排空、本地名额已满，则暂时拒绝新请求（仍是
  429 `concurrency_limited`），从而保证**本实例该租户任意时刻运行总数
  `<= maxConcurrent`**：旧占与新占合计不超额；同一个请求只在本地或后端
  其中一侧计数，不会被两处重复计数而误拒；
- 随着遗留请求陆续结束、本地名额归还，系统平滑收敛回纯后端计账，无需
  人工干预。

> 多实例下后端不可用时各实例只能各自执行本地硬上限（无法跨实例交换
> 在途信息）；后端恢复后由集中计账重新收敛全局一致。这是 fail-open
> 在分区期的固有边界，文档明确、指标可解释。

### 7.3 级联故障防护与可观测性

- 每次存储调用都带超时（连接/脚本级），后端慢或不可达不会无限阻塞 worker；
- 续租调用失败只记指标并在下个周期重试，只有持续失联超过 TTL 才丢约；
- 健康监测（默认 1s 探测）只在**状态翻转**时记录日志，避免故障期日志风暴；
- 后端恢复后请求立即恢复正常判定，不残留降级状态。

拒绝原因与当前状态通过结构化日志与 `/debug/vars`（expvar）指标观测：
请求/放行/拒绝（按租户、接口、原因）、降级动作、降级期本地在途数、
正常在途数、续租失败次数（`lease_renew_failed_total`）、凭证丢失次数
（`lease_lost_total`）、后端健康、配置版本、判定延迟等。
